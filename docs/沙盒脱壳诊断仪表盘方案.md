# mHook 沙盒脱壳「诊断仪表盘」方案

> 目的：把沙盒脱壳从"黑盒轮询抓 dex"升级为"带入口记录 + 可复制日志文件的手术报告"，
> 让任何一次脱壳失败都能直接看出：壳走到哪一步、我们拦截到没有、dump 出来是不是真身。

---

## 一、现状（基于代码事实）

沙盒脱壳 = **BlackBox 虚拟容器 + MemoryDexDumper（Xposed hook）**。

MemoryDexDumper 目前的拦截维度（`MemoryDexDumper.java`）：

| 维度 | hook 点 | 抓什么 | 说明 |
|---|---|---|---|
| A | `InMemoryDexClassLoader` 构造 | ByteBuffer dex | 内存加载的壳（D8 后段） |
| B | `DexClassLoader` 构造 | 磁盘 path | 磁盘解密的壳 |
| C | `DexFile` 构造 | 磁盘 path | 同 B 变体 |
| D | 兜底轮询 | 已加载 dex cookie → Unsafe 读 ART 内存 | BlackDex 思路，抓延迟/间接加载 |
| - | `loadClass` | （**刻意不 hook**） | 注释写明：频繁触发原生内存读取，易被阿里 Ashield 这类壳检测崩溃 |

触发方式：后台线程在 **3/8/15/25/40/60 秒**各枚举一次 + 轮询 `dump_now` 标志文件（UI「立即脱壳」）。

### 现状的问题（无观测 = 瞎猜）

1. 不知道壳**是否触发了** A/B/C/D 任意一条路径——抓到了算撞运气，没抓到无凭据。
2. `dumpDex` 只认 dex magic；**抽取出壳/方法体为 0x0000 的"骨架 dex"也会被保存**，看起来成功实则无用。
3. 看不到**失败链**：是没走我们 hook 点（壳路径异常）？还是走了但读取失败（ArtDexFile 偏移不对/权限）？
4. dump 结果在私有目录，**无法直接复制/导出**。
5. 没有一站式"这次沙盒运行到底经历了什么"的报告。

## 二、目标能力（Layout Inspector 式）

### 1. 入口/生命周期日志流（事件日志）
在以下时机**一律记录一条带时间戳的事件**：

```
[+0.012s] Application.attachBaseContext()        pkg=xx.xx.xx
[+0.013s]  System.loadLibrary("libshell-super")  libpath=/data/.../libshell-super        hit=YES(dumped 0)
[+0.015s]  DexClassLoader.ctor                    path=.../classes2.dex   size=78KB   magic=YES
[+0.015s]    └ dumpDex: 保存成功 -> sandbox_dump/xx/classes2.dex   methods_ok=24, empty=3
[+0.020s] InMemoryDexClassLoader.ctor             bufferPtr=0x... bufSize=23.4MB magic=YES
[+0.020s]    └ dumpDex: 保存成功 -> sandbox_dump/xx/inmem_1.dex     methods_ok=9477, empty=0  完整
[+0.030s]  loadClass（未 hook，跳过）
[+3.000s]  定时枚举: 新增 cookie=0x7f... -> 新 dex? NO（已 dump）
[+15.00s]  定时枚举: 新增 cookie=0x8a... -> 新 dex? YES -> artDex read ok -> inmem_2.dex
```

### 2. HOOK 命中仪表
每个 hook 点统计：
```
hook命中统计:
  InMemoryDexClassLoader : 触发 3 次, 有效 dex 2 个
  DexClassLoader         : 触发 1 次, 有效 dex 0 个, magic=NO(可能为碎片或壳自 load)
  DexFile                : 触发 0 次
  定时枚举(30s 窗口)      : 命中新 cookie 1 个, 读出 1 个
  loadClass              : 未启用(防检测)
```

### 3. 产物体检（不只是 magic）
每个保存的 dex 附加健康度报告：
```
文件: classes2.dex (78KB)
  dex magic        : YES (035)
  class_defs_size  : 24
  方法抽查         : 24 个有方法体, 3 个 insns 全 0x0000(疑似抽取)
  字符串池可读     : 92% 可打印  (低→疑似字符串加密)
  判定             : ⚠️ 疑似方法抽取壳(骨架dex), 需动态补码或放弃
```

### 4. 日志文件导出（可复制）
```
写入位置: /storage/emulated/0/Download/mhook_dump/sandbox_<pkg>_<yyyyMMdd_HHmmss>.log
内容     : 上述全部事件流 + 命中统计 + 每个 dex 体检表 + 最终结论
格式     : 纯文本(UTF-8)，可直接分享/喂给 AI 分析
```
> 与现有脱壳 dex 同级目录（`Download/mhook_dump`），用户可用文件管理器直接拷出。

## 三、落地改造点（只列位置与思路，均轻量）

| 位置 | 改什么 |
|---|---|
| `MemoryDexDumper` 内新增 `DumpLogger` 单例 | 线程安全 append 到内存缓冲 + 定时/结束时写文件 |
| `hookInMemoryDexClassLoader/hookDexClassLoader/hookDexFile` | 每个 hook 触发时 `DumpLogger.event(...)` |
| `scheduleDumpAll` 各时间点 | 每次枚举前后记事件 |
| `dumpDexPath/dumpDex` | 记录 magic 判定、保存路径、大小 |
| `dumpDex` 后新增 `inspectDex` | 解析 class_defs/method 数、抽查 codeItem、字符串可读比 |
| 脱壳结束（`SandboxDumpActivity`） | 收尾写文件 + 把日志路径随 zip 或单独提示 |
| 插件进程数据写公共目录 | 走 BlackBox 提供的 IO 适配或 `FileProvider`/ContentProvider 桥（避免虚拟进程直接写 /sdcard 的权限坑） |

预估改动：2~3 个文件、约 200~300 行，**不动 dump 核心逻辑**，纯加观测。

---

## 四、这份方案能回答的核心问题

- **这个壳到底脱不脱得动？** → 看命中统计：A/B/C 全 0 命中 = 壳没走标准加载路径（反沙箱/自解密），判定"需他法"；D 兜底大量命中但方法全是空的 → 此壳是抽取型。
- **为什么 dump 出来打不开/没方法体？** → 体检表直接标"疑似抽取"。
- **是壳太强还是我们 bug？** → 事件日志能看出是"没走到 hook"（壳问题）还是"走到了但 read 失败"（我们问题）。
- **下次怎么改/喂 AI？** → 日志文件本身可复制，直接给 AI 或经验者看。

---

## 五、边界与风险（诚实说明）

1. **loadClass 不 hook** 是当前刻意选择（防 Ashield 崩溃），日志里会明确标注"未启用"，避免误读为失败。
2. 方法体体检是"抽查"不是全量解析（性能），对抽取占比有个置信区间，非 100% 精确。
3. 虚拟进程写公共目录有权限坑，需走容器 IO 适配；若短期麻烦，可先落私有目录 + UI 提供「导出日志」按钮，功能等价。
4. 日志本身不影响脱壳成功率——它是"看得见"，不改变"能不能抓到"的上限。对反沙箱壳，"看得见它拒绝了"就是最大价值。

---

## 六、结论

可行，且是**投入产出比最高**的一步：
- 不改脱壳算法，只加观测 → **所有沙盒脱壳都变成可诊断的**；
- 每次失败都有"为什么"的依据，AI 或人工都能直接接手；
- 与「AI 脱壳」天然互补：日志给 AI，AI 给下一步方向。

不建议先做"万能脱"（工程量/成功率都不可控），建议先做"看得见"。
